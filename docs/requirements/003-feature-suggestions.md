### ② 「多站直达」升级为「多站比价」

**建议**：加一个「🔍 比价」按钮 —— 在当前页 `fetch` 这几个站的搜索页，

这和已有的「补全头像资料」是同一个限制。

**建议范围**：只做「显示评分对比」，**不要**做成自动下载。

## 二、值得做（中等成本、明确收益）

### ④ 规则影响面预演（全站 dry-run）

**现状**：`estimateImpact(value, type)`（`content.js:2782`）已经存在，
但它只能基于**本地发现库**估算——发现库里没有的内容它算不出来。

**建议**：新增「影响面预演」页签 —— 你写一条规则，扩展列出**当前页（或最近浏览过的页）
里所有会被它命中的卡片**，灰色高亮、可逐张确认。

**为什么值得做**：
- `content.js:1359` 的 `previewMode`（规则预览）已经是**单页版**的雏形
- 你的痛点是「怕误杀」（`auditWarn` 设置项就是为这个加的）
- 纯本地、零网络请求，风险低

**与 previewMode 的区别**：previewMode 是「全局开关，开启后看所有规则的着色」；
预演是「针对**某一条待建规则**，当场告诉你它会杀掉什么」。后者在**建规则之前**就能拦住误操作。

### ⑤ 备份自动快照 + 一键回滚

**现状（我一开始写错了，这里更正）**：`autoBackup` **是有实现的** ——
`background.js:625` 的 `autoBackup()` 会把整库 JSON 下载到
`下载目录/sitefilter-backup/sitefilter-<日期>.json`，由 `sf_backup` 定时器
（`background.js:806`，每 24 小时）和启动时（`:827`）触发。

**但现有实现有两个缺口**：

1. **只有单点，没有历史**。`conflictAction: 'overwrite'` + 文件名只带日期 ⇒
   同一天多次备份会互相覆盖，**恢复不了「昨天下午 3 点那份」**。
2. **只能恢复整库**。出了问题要么全量回滚，要么不动。而最常见的事故是
   「规则被改乱了」，只想回滚规则，不想丢掉这两天新积累的发现库。

**建议**：
- 文件名加时间戳（`sitefilter-2026-09-22T1530.json`），保留最近 7 份，超出滚掉
- 在设置页加「历史快照」列表，支持**整库回滚**和**仅回滚规则/分组**
- 现有的 `undoStack`（`options.js:140`，40 步）只在设置页会话内有效，
  关掉就没了 —— 快照是它跨会话的补充，不是替代

**为什么值得做**：`chrome.storage.sync` 有配额，误删后云同步会跟着被覆盖；
手动导出又要记得点。定时落盘是唯一的自动兜底，而它现在已经跑起来了，只差「保留多份」。

### ⑥ 番号站补足 —— 见需求 002 的 L2

需要先做**真实页面验证**（见需求 002 第 4.5 节）。我的建议是先做三档、发一版，
再单独验证番号站翻页，最后决定要不要做补足。

## 三、慎重（技术上能做，但有代价）

### ⑦ 自动识别番号 → 跨站找高清 / 磁力

这是你**最初**提的那个需求，我要认真说明为什么把它放在「慎重」。

**技术上完全可行**：`CODE_SITES` 已有 4 个番号站的搜索模板，
`probeLinks()`（`content.js:3170`）已经能解析磁力 / 种子 / 网盘链接，
`MAGNET_RE` / `TORRENT_RE` 都有。拼起来就是一个「输入番号 → 查 4 个站 → 汇总磁力」的功能。

**但有三个硬问题**：

1. **CORS 是死结**。扩展的 `content script` 只能 `fetch` 当前页同源的资源。
   要请求 `javbus.com`，你得**正开着 javbus.com**。真正的跨站请求需要：
   - 要么在 `manifest.json` 里给这些域加 `host_permissions`（会让安装时的权限提示变长，
     可能影响商店审核），然后走 `background.js` 发请求；
   - 要么让用户手动开一个标签页。
   当前 `matches` 是 `<all_urls>`，但 content script 的 `fetch` 仍受同源限制，
   `background.js` 则没有 host 权限就发不出去。

2. **「最高清」是个无法自动判定的量**。评分能抓、时长能抓、分辨率能抓，
   但「哪个版本是最高清」在这类站点上往往靠上传者描述，
   自动判定会给出**看起来很确定但其实不可靠**的结论。这比不做更糟。

3. **反爬与合规**。批量抓 4 个站的搜索页，频率一高就会被封 / 上验证码；
   扩展如果被商店认定为「爬虫工具」有下架风险。

**我的建议**：**不要做「自动找最高清」**，改成 ② 的「多站比价 + 一键跳转」——
把判断权留给你，扩展只负责**省掉复制粘贴和开标签的机械动作**。
这样风险最低，收益也拿到了大头。

### ⑧ BT 客户端 / 下载器集成

收藏器（`universal_web_collector_v9`）已经在做真正的下载编排，
扩展侧已经有 `nativeMessaging` 权限 + `collector-native.js` 桥。
让扩展把磁力直接丢给采集器或 qBittorrent 技术上顺理成章。

**但我不建议现在做**，理由：
- 采集器的**数据保留门禁还没关闭**（Task 1–3 的记录和产物消失，原因未知）——
  在这个前提下加新的落盘入口，只会让排查更难
- 扩展的定位是「浏览时的过滤器」，一旦能批量下载，性质和商店分类都会变
- 真要连，也应该由采集器那侧主动拉，而不是扩展推

## 四、不建议做（我会明确反对）

### ⑨ 引入构建工具 / 框架

当前是**零构建的 vanilla JS**，`content.js` 3912 行 / `options.js` 2699 行，
配 15 套原生测试 + `ci.py` 门禁，跑得很顺。

引入 Vite / TS / React 的代价：构建链维护、调试时看不到源码、MV3 的 CSP 限制、
测试要重写。**收益接近于零** —— 这个项目的复杂度根本不在 UI 层。

> 唯一让我动摇的点：`content.js` 3912 行确实已经很大了。
> 但这可以用**拆分文件**解决（MV3 的 `content_scripts.js` 支持数组，
> 现在已经是 `['expr.js','content.js','xchina-download.js']`），
> 不需要引入构建工具。这可以作为独立的小重构提案。

### ⑩ 规则包云分享 / 社区规则

和「数据 100% 本地存储，不上传任何信息」（`manifest.json:5` 的 description）
直接冲突。而且规则本身高度个人化，共享价值有限。

## 五、还有一个我想提的：`content.js` 的体量

3912 行单文件、约 170 个函数，已经到了「改一处要翻半天」的程度。
`manifest.json` 的 `content_scripts.js` 已经是数组，**拆文件是零成本的**：

```
content/state.js      数据读写 + migrate
content/extract.js    卡片识别 + extract
content/rules.js      规则匹配 + decideCard
content/panel.js      面板 UI + 渲染
content/index.js      boot / observe
```

好处：改规则逻辑时不必在 3912 里找；测试也能按模块加载。
坏处：MV3 content script 共享同一个执行环境，拆分只是**文件级**的，
不能真的模块化（没有 import），要靠全局变量串联 —— 需要注意顺序。

**这个我不建议现在做**，因为会影响 `_test_*.js` 里 `win.eval(code)` 的加载方式
（现在都是单文件读入）。等需求 002 落地、测试稳定后再单独做一轮重构比较合适。
